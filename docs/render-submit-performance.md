# 渲染提交优化与测量口径

版本：`2026-10-27-render-submit-v3`，2026-10-27。

## 本轮变更

- `render` 保留原有总量口径，拆出 `render.interpolation`、`render.canvas`、`render.panels`。面板有 14 个子项，重力场和角色头顶指示补上计时。
- `render.monsters` 包含在 `render.entities` 中；`render.panels.*` 包含在 `render.panels` 中。父子项不能重复相加。
- 附近按钮仅在目标、文字、辅助名称、显隐和位置改变时写 DOM；共用帧内容器几何，并在写坐标之前读完按钮高度。
- 任务 HUD 先读取各卡片高度，再批量写位置；稳定状态不清除再重写 top。秘境切换仍先恢复任务卡的 CSS 位置，再排列领主条。
- 本轮没有改变模拟步长、插值算法、怪物动画、文字绘制、DPR 或资源图集。

## 指令采样

主场景上下文每 300 帧采样 1 帧，关闭诊断或非战斗时不采样；最多保留 12 帧。仅采样帧临时包装方法，`finally` 恢复原属性，包括绘制抛异常的情况。用户清空日志时同时清空指令样本。

导出路径为 `rendering.canvasCommands.samples`，每种方法包含 `count`、`totalMs`、`maxMs`。采样帧在帧记录中标记 `canvasCommandSample`，样本标记 `instrumented`。观察属性恢复后不会留下全局原型修改。

这些数值是同步 API 调用返回前的耗时，含测量误差；不是 GPU 完成时间。不覆盖离屏画布、属性赋值、浏览器后续栅格化或合成。浏览器计时精度常为约 0.1ms，单次调用显示 0 不表示免费；单帧排名可能受调度和 GC 干扰，应结合多帧总量及对应阶段判断。采样帧的整体成本也被诊断包装影响，不能当作无测量开销的基准帧。

## 浏览器实测

独立 Chrome 会话，同一机器、相同存档夹具和代码绘制器；默认服务为 4175，本次因被其他任务占用使用 4185。以下数字不是华为 Mate 50 Pro 的温度、功耗或长期帧率结论。

| 检查 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 原场景附近面板平均同步耗时 | 3.13ms | 0.14ms |
| 原场景全部每帧面板平均同步耗时 | 4.86ms | 1.74ms |
| 原场景 render 总平均同步耗时 | 13.85ms | 10.45ms |
| 工坊同一按钮交替批次，单独调用 render | 4.26ms/次 | 0.082ms/次 |
| 稳定按钮连续调用 100 次的 DOM 变化 | 未作为原版指标采集 | 0 次 |

前三行是两次运行的相同场景窗口，不是手机 FPS 倍率保证；交替批次只衡量单个控件，不能按其百分比推算整帧收益。

名称贴图缓存进行了实际实验但撤下：30 怪物的每帧文字提交从 30 次描边 + 30 次填字变成 30 次贴图，包含身体的总同步提交均值却从 1.47ms 升到 2.13ms。因此正式代码保留原文字，不新增标签位图内存。

后续 30 怪物运行样本记录到每帧 747 次 fill、515 次 stroke、30 次 drawImage、39 次 fillText、30 次 strokeText。单帧累计同步时间约为 fill 1.0ms、stroke 0.9ms、drawImage 0.4ms、两类文字各 0.2ms。beginPath 也记录到 0.9ms，但其中一次占 0.7ms，不能据此认定 beginPath 本身比贴图更昂贵。

该较重场景的附近面板仍可达约 3.89ms：按钮自身的稳定写入被消除，但其他面板的样式修改、工坊安全区和按钮高度查询仍可能引发布局。下一步应结合浏览器 Layout 调用栈继续合并跨面板几何读取；本轮不宣称全部布局成本已经消失。

## 验证与证据

- 直接相关的性能记录、Canvas 采样、HUD 几何与帧内几何共 19 项 Node 测试通过。
- `tests/render-submit-browser.cjs`：正式循环分段结束完整、导出指令可用；320/390 手机视口与宽视口昼夜同屏，无页面溢出。
- `tests/render-submit-hud-browser.cjs`：16 组工坊/尺寸/昼夜组合；6 组任务与秘境布局切换；实际点击打开原工坊并关闭；稳定状态无重复 DOM 修改，资源变化和暂停立即更新。
- `tests/render-submit-command-browser.cjs`：真实更新循环中的 30 怪物指令采样。
- 额外执行建筑入口和邻居交互旧用例时共 4 项失败；已在未修改的主分支复现相同失败。建筑夹具缺少 progress.restoration，邻居用例与当前修复/居民规则不一致，本轮未修改这些逻辑。
- 证据目录：`output/playwright/render-submit/`。`result.json` 为被否决的文字缓存实验；`final-browser.json` 为正式优化结果；`hud-browser.json` 为控件交替基准及交互验收；`commands.json` 为 30 怪物样本。
- 接入主分支的并行 PNG UI 更新后，重新运行正式循环与 HUD 浏览器验收；6 组战场昼夜视口、16 组工坊视口、6 组任务/秘境布局均通过，资源变化和暂停状态正确。证据为 integrated-browser.json 与 integrated-hud.json；以上性能对照数字取接入前的独立优化实验，不混用不同资源版本。
- UI 视觉记录见 [任务单](art-tasks/render-submit-performance.md)。没有运行全量测试，也没有实测手机持续 30 分钟的温度降频。

## 手机复测

刷新到上述诊断版本后，在同一设备上复现兽潮与长时间运行并导出。优先比较 `render.canvas`、`render.panels.nearby`、`logic` 和 `outside`，再对照指令样本。若 outside 明显增大而同步提交稳定，需要 Chrome Main/Raster/GPU/Compositor 时间线继续定位，不能直接认定是绘图 API 或发热造成。
